# Vesuvius contribution: correct validity during TIFXYZ resizing

**Implemented and locally validated.** Prepared September 7, 2026 for a Progress Prize entry. No maintainer acceptance or award is established.

When the public `upsample_coordinates` API resizes an original PHerc0800 surface, its old validity mask accepts points whose coordinates incorporate missing-vertex values. The fix aligns validity checks with OpenCV's actual interpolation support. It preserves the coordinate interpolation itself, recovers wrongly rejected valid points, and leaves nearest-neighbor output unchanged.

![Measured before/after geometry](evidence/PHerc0800_before_after.png)

The top plots use native X/Y coordinates and independently fitted axes to make the original surface and contamination visible. Red marks accepted output points whose interpolation includes missing source vertices. The lower row shows source and output masks. No CT image, ink detection, letters, or historical content is generated by this figure.

## Real-data results

Each input is an untouched original PHerc0800 segmented surface from the official public S3 bucket. The stored grids are 93×95, 90×84, and 42×42; each is resized to approximately 20× in both axes using its own metadata scale and target_scale=1.0. The realized shapes are 1860×1900, 1800×1680, and 840×840.

Totals across the three patches: **74,100 linear and 71,700 cubic accepted output points with invalid source support become zero**. These are output sampling locations, not independent discoveries or a count of physical defects. The same number of previously rejected, fully supported output locations is recovered in these fixtures. All coordinates accepted by both versions are bit-for-bit identical. Invalid output coordinates are consistently (-1,-1,-1).

The linear result has a second direct geometric check: on the 90×84 patch, 28,184 accepted baseline outputs escape the source bounding box by more than one native coordinate unit, compared with zero after the fix. Linear interpolation of valid finite vertices cannot leave their convex hull. Cubic interpolation can overshoot legitimately; cubic bounding-box escape alone is not our correctness oracle.

## Method and implementation

Source base: `d8c5f488a105286c548c99c5f7c7ad9f29e3ed14` in ScrollPrize/villa. Original `upsampling.py` is preserved under `baseline/` with a hash in `evidence/real_mesh_results.json`.

The old implementation resizes coordinates with linear/cubic interpolation but resizes an eroded validity mask with nearest-neighbor interpolation. Their inverse sample positions differ. The new helper checks separable support using the realized output dimensions, OpenCV's float32 half-pixel mapping, and replicated edge taps. Integer source positions use the center sample. Explicit branches match OpenCV's identity copy and exactly twofold linear/area downsample paths, including wide arrays beyond float32 integer/half-integer precision.

An independent oracle constructs horizontal and vertical basis impulses through the installed OpenCV resize operator. Absolute coefficient weights prevent cubic cancellation from hiding invalid influence. It ignores only weights at or below 1e-12; observed small-case excluded residues are around 1.39e-17. This is a finite-coordinate, finite-sentinel check, not a proof about NaNs, infinities, every backend, or every dimension.

Code is confined to `vesuvius/src/vesuvius/tifxyz/upsampling.py`; focused regression tests are in `vesuvius/tests/tifxyz/test_upsampling.py`. No new production dependency, model, training change, or interpolation-precision change is introduced.

## Validation and independent review

- 53 focused regressions pass with OpenCV 5.0.0 and 4.14.0 on macOS arm64, Python 3.14.6, NumPy 2.5.3. The OpenCV 4 package is isolated under `.cv4`, leaving the main runtime at OpenCV 5.
- 21 nearby surface-preflight and I/O tests pass.
- The original baseline fails the support regression; this is recorded as an expected failure, not an unresolved final failure.
- An independent review caught identity and exact-half-size failures in the first candidate. Historical receipts remain in `tools/large_*_numeric_review.json`; the final implementation adds both fast paths and four large-array regressions. Those receipts do not describe the final code.
- All 21 acquired originals pass SHA-256 checks before and after the real-data run.
- Timing uses one warmup and three complete calls per input/order/version in the same process, OpenCV one thread and BLAS/OMP one thread. Raw samples and min/median/max are retained. This is a correctness fix; modest additional cubic-mask cost is visible in the table. No speedup is claimed.
- Linux, Windows, other OpenCV backends, and the complete ML/training suite were not executed. No GPU or paid compute was used.

## Contribution relevance and remaining limits

The demonstrated use is directly resampling a real public papyrus mesh through this exported API. A bounded current-source search found no internal call sites of `upsample_coordinates` beyond its definition and public export. Existing community use, maintainer demand, adoption, and downstream CT/ink improvements are not established. This is a technically validated contribution candidate, not a demonstrated unwrapping breakthrough.

Only three patches of one scroll were evaluated. They share isotropic scale≈0.05; anisotropic and boundary handling are covered by supplemental controlled tests, not additional real-scroll validation. Their original metadata and the current volume registry have different physical-scale provenance, so all reported geometry remains in native coordinate units.
